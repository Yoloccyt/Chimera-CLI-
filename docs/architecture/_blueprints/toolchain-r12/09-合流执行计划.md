## 4. 分批顺序（按"冲突性质"而非文件顺序）

> 原则：**先合"由工具派生、手抄必错"的文件，再合代码**；每批独立可验、独立可退。

### B1 · 派生基线（必须先合，否则后续门禁读数全是假的）

对象：`scripts/{fnlen_baseline, lock_await_freeze, await_guard_allowlist, contract_zero_consumer, contract_consumer_baseline}.txt`

**处置原则：不手工合并文本，而是"取合并后代码 → 用工具重算 → 写回"。**
这些文件是**派生面**（由扫描器产出），手抄会产生"比它描述的代码活得久"的假基线。
- 先把两侧代码合完（B3~B5），再对每个基线跑其生成器（`--write` 模式）重算；
- 若某基线无 `--write` 能力，则该文件按"以我方为准 + 逐行复核对方新增键"处置，并在报告里写明为何不能重算。

**验收**：对应门（G-119 / G-91 / fnlen / await 四门）rc=0。

### B2 · 治理脚本与 CI（`gate_manifest.toml` / `perf_thresholds.toml` / `bench_check.yml` / `ci.yml` / `check_perf_redlines.py` / `test_govd.py`）

**处置原则：以"键集对拍"判决，不以文本合并判决。**
- `perf_thresholds.toml` ↔ `bench_check.yml` heredoc 是**机器双向对拍**（I9/I10）：两侧各自的键都要保留，然后跑 `check_perf_redlines.py --static-only` 验证键集一致；
- `gate_manifest.toml` 两侧新增的门（我方 G-145~G-148 待登记、对方新增若干）**取并集**，编号冲突按"先到先得 + 后到顺延"并同步改 `spec_ref`；
- `check_perf_redlines.py` 是我方 453 行 / 对方 150 行的真冲突：**先读两侧差异再决定**，禁止 `-X ours/theirs`。

**验收**：`py scripts/check_perf_redlines.py --static-only` rc=0；`python scripts/run_gate_manifest.py --jobs 2`（light 门）rc=0。

## 5. 停工条件（遇到即停，不硬推）

| 条件 | 处置 |
|---|---|
| 某批验收红且 3 次修不动 | 停在该批，`git merge --abort`（或退回 batch 起点），出缺口报告 |
| 两侧对同一不变量给出**相反**语义（如 ADR-235 D1「副作用默认 Write、hint 显式信任」vs R11 D1「空集=恒串行」） | **停下请人裁决**，不在合并中私自选边 |
| 治理脚本（`check_perf_redlines.py`）需要重写判据才能合 | 停，先出方案 |
| 磁盘/内存不足（`--workspace` 编译需要余量） | 停，先清 |

## 6. 回滚

| 层级 | 方式 |
|---|---|
| 单批 | 在合流 worktree 内 `git checkout -- <该批文件>` 重来 |
| 整次合并 | `git merge --abort`（未提交时）／删 `merge/toolplane` worktree（已提交但未推） |
| 已合入主分支 | `git revert -m 1 <merge-commit>`（保留历史，不重写） |

**红线**：不合流完成前不 push、不打 tag；不 `git add -A`；不用 `-X ours/theirs` 做策略性合并（除 T3 明确列出且经复核的文件）。
