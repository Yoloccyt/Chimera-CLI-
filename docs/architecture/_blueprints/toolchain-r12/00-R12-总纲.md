## 2. 现状判定：14 条硬结论

> 每条都能被独立复核。标【实测】者为本次在本机或历史存档上取到的数值。

### 2.1 关于"性能到底慢在哪"

| # | 结论 | 证据 |
|---|---|---|
| **F1** | 单次工具派发的**固定成本**是 1.06 µs（seccore 链）；传输地板 80.58 ns | 【实测】`dispatch_chain/chain_seccore_route_hit` 1.06 µs、`dispatch_layers/floor_echo_transport` 80.58 ns（本轮同轮跑） |
| **F2** | 沙箱门已做过一次 6.7× 优化（逐次 clone 策略 → 派生策略记忆化） | 【实测】`sandbox_check_seccore` 819.57 ns vs `legacy` 5.52 µs |
| **F3** | 因此：**当工具真实服务时间是毫秒级时，链路开销占比 ≈0.003%**，微优化没有收益空间 | 由 F1 + MCP 2PC 实测 30.67 ms（`mcp_mesh_transaction/2pc/1`）推出【推断】 |
| **F4** | **批量并行已达理论上限**：64 个 1 ms 任务，串行 998.81 ms → 8 路上界 125.36 ms = **7.97×**（理论上限 8×，效率 99.6%） | 【实测·存档 2026-11-12】`tool_batch/serial_ms1/64` vs `parallel_ms1_bound8/64` |
| **F5** | **但零延迟下并行反而更慢**：64 个零延迟任务，串行 44.41 µs → 并行 51.27 µs（+15%） | 【实测·存档】`tool_batch/serial_ms0/64` vs `parallel_ms0_bound8/64` ⇒ 小任务并行是负收益 |
| **F6** | PlanRunner 单层只读并发也已达上限：8 个 2 ms 节点，c=1 124.42 ms → c=8 15.66 ms = **7.94×** | 【实测·存档】`toolplan_layers/readonly8_ms2` |
| **F7** | 混层写屏障分段有效：7 读 1 写，c8/c1 = **3.98×**（结构上限即 4×：读段 1 个延迟 + 写 1 个延迟） | 【实测·存档】`toolplan_layers/mixed7r1w_ms2` |
| **F8** | MCP 2PC 的多参与者扇出**已经并行**：1/3/5 个参与者耗时 30.67 / 30.74 / 31.24 ms（墙钟 ≈ max 而非 Σ） | 【实测·存档】`mcp_mesh_transaction/2pc/{1,3,5}` |

**F4~F8 合起来的结论（本方案最重要的一条）**：**"提高并发数"不是 R12 的题目**。
本仓现有并行设施在"单层/单批"内已经打到硬件与结构上限；再调大只会过订阅。

## 3. 根因模型：四条因果链

### 链 A — 上下文冗余（为什么"改装配面参数"没用）

```text
R9 建了 assemble_context（去重两档 + 单一预算账本）
   └─ 但从未接进生产（F9）
        └─ 生产走 TUI 精确档（弱）+ mca 无去重（更弱）
             └─ 工具响应恒保留且权重最高（C4）、每轮重建临时窗口（C5）
                  └─ 压缩只在 L3 溢出才跑（C6）
                       ⇒ 冗余不是"算法不够好"，是"算法没上岗"
```

**处置**：W1 先接线，且必须带"关掉逐字节等价旧路径"的等价性测试。**不要**先调 0.92 阈值或 dedup 开关。

### 链 B — 检索延迟（两个可修的确定性缺陷）

```text
recall_by_clv 持读锁算全量余弦（F12①）
   └─ 与并发召回/并发装配互相阻塞（读锁互斥写）
        └─ p95 抖动随并发度放大
memory_graph 阈值不连续（F12②）
   ├─ 1000 条目 = 426.88 ms（O(n²·512)）
   └─ 2000 条目 = 102.20 ms（HNSW）
        ⇒ 规模翻倍反而快 4 倍，容量规划无法建模
```

**处置**：W2 两处都改，且都带结构判据（锁空出探测 / 单调性断言）。

### 链 C — 跨会话一致性

```text
cmt 无生产者 ⇒ 热/温/冷分层恒空 ⇒ INV-8 单调性无对象可验
schema_version 只写不读 ⇒ 版本面形同注释
自愈只判尾部 ⇒ 中段缺口不可见
```

**处置**：W3 三处都补，且把"灌 1 万条 → 强杀 → 重启零缺口"作为 L1 判据。

### 链 D — 并行度（真正剩下的三个增量）

```text
① 屏障形状：均匀负载收益 ≈0.4%（F15），偏斜负载才有值 ⇒ 需先造偏斜基准再决定默认
② 跨面过订阅：六面各 8（F14）⇒ 需要共享预算（R12 真增量）
③ 生成/执行重叠：未接线（F16）⇒ 需 LLM 流式面，当前只能做接缝（条件项）
④ 资源冲突判定缺失：写不同资源也串行（AccessSet 不存在）⇒ R12 真增量
```

## 4. 目标架构

### 4.1 上下文层：一条装配链，三个入口

```text
               ┌────────────────────────────┐
  TUI 策展 ───►│                            │
  LLM 通道 ───►│   assemble_context (L2)    │──► 单一预算账本 ──► 模型
  MAS 上下文 ─►│   去重三档 + 折叠 + 驱逐   │
               └────────────────────────────┘
                      ▲
                      │ origin_ref（跨轮折叠的唯一前提）
               ContextOriginRef
```

**不变量**：装配输出必须是输入 `seq` 的**保序子序列**（08 文 §3.1 第 3 条断言）。

### 4.2 记忆层：锁外计算 + 连续阈值

```text
recall_by_clv:
  read() ─► Arc::clone(entries) ─► drop(read) ─► 余弦计算（锁外）─► Top-K
memory_graph:
  n < min_threshold ─► 精确 O(n·512 + n log n)      （阈值以下）
  n ≥ min_threshold ─► HNSW 候选 + 精算 Top-K        （阈值以上）
  保证：build(n) 单调不增（新增断言 graph_build_monotonic）
```

### 4.3 调度层：一个平面，四个执行面共用预算

```text
        ┌──────────────────────────────────────────┐
        │  SchedulingPlane (L7, gqep-executor)     │
        │  ├─ 依赖判定：D-A 边 / D-B 副作用 / D-C AccessSet
        │  ├─ 准入：ready-queue（就绪即调度，默认 legacy）
        │  ├─ 资源：ResourceGovernor（Off/Observe/Apply）
        │  └─ 遥测：ScheduleSnapshot → ScheduleSink
        └───────▲──────────▲──────────▲────────────┘
                │          │          │
          PlanRunner   BatchLimits   action/delegation
          (E1/E2)       (E3/E4)       (E5/E6)
```

**关键**：调度平面**不做抢占**，只做准入；`Off` 档必须逐字节等价于现状。

## 5. 十条设计决策与减法

| # | 决策 | 理由 | 反例（若反过来做） |
|---|---|---|---|
| **D1** | 不新建 crate，全部挂 `gqep-executor` / `nexus-contracts` / `hcw-window` / `mlc-engine` 既有位置 | 46 成员 + 可达性棘轮；Ω₆-Reuse | 新 crate 要过 §3.1 索引 + ADR + 棘轮登记 |
| **D2** | 上下文线**先接线后优化** | F9：内核未上岗 | 调参数 = 改测试里的行为 |
| **D3** | 召回评分**锁外化**（快照 → 释放 → 计算） | §4.4 反模式 1；`faae-router` 已有同款先例 | 持锁算余弦，并发度越高越慢 |
| **D4** | 建图阈值**连续化**（`>=` + 精确路径 O(n log n) 化） | F12② 的 4 倍倒挂 | 容量规划不可建模 |
| **D5** | 调度面**合流不重写** | 分支已有 `run_with`/`build_graph`/10 例/4 变异（ADR-233 追加节一） | 两套调度器，合流时手工解冲突 |

| **D7** | 跨面预算用**注入式 Governor**，不用全局静态 | 全局静态会污染并行测试（criterion 与 `#[tokio::test]` 同进程） | 测试互相干扰 |
| **D8** | 遥测只放**有限取值域**（计数/比率），不放工具名/路径 | 高基数会打爆时序库（`batch.rs:109-119` 已记教训） | 指标系统不可用 |
| **D9** | 每个行为变更**必须带 env 逃生 + 关掉逐字节等价** | R11 的既有纪律 | 出问题只能 revert 全部 |
| **D10** | 判据四层（L1>L2>L3>L4）+ 禁四种证明 | ADR-234 原典 | "跑得快了"变成不可复核的断言 |

### 减法表（明确不做，且写明重开条件）

| 不做 | 理由 | 重开条件 |
|---|---|---|
| 提高任何一处并发上界（8 → 更大） | F4/F6 已达理论上限；F5 显示小任务并行是负收益 | 出现服务时间 ≥10 ms 的工具族且实测队列深度长期等于上界 |

## 10. 结论（给决策者的一句话版本）

**本仓的"性能"问题不在工具执行链的微秒级开销（1.06 µs，占比 0.003%），也不在并发数不够（单批已达 7.97×/8×）。
真正的三块硬骨头是：上下文装配内核没上岗（F9）、两个可修的检索缺陷（F12）、以及调度面与一条未合并分支的双向分叉（F14/A7）。
R12 因此把 60% 的工程量投在"接线 + 修复 + 合流裁决"，把 40% 投在真正的新增量（AccessSet 冲突判定、跨面预算、遥测与门）。**

## 11. 与《HCW 上下文架构重构蓝图 v3.0》的对接

蓝图（仓库根，225 行）定了 P0~P3 四阶段。R12 **不改它的设计**，只把"已交付但没上岗"的部分接上，并指出一个影响它全部配额设计的事实。

| 蓝图阶段 | 蓝图交付物 | 仓内状态 | R12 的关系 |
|---|---|---|---|
| **P0** 能力档案 + 有效窗口探针 | `ContextCapabilityProfile`（L0） | 已落（ADR-291）；类型在 `crates/nexus-contracts-mca/src/mca/context_capability.rs` | 不动；但 W0-3 要处理它在 `nexus-contracts` 的**登记错位**（正是 2 红测试的成因） |
| **P1** HCW v3 分层重参数化 + `WindowGovernor` | `WindowPlan{resident_cap, page_budget, tier_allocation}` + `StaticGovernor`/`AdaptiveGovernor` | 类型与实现都在 `crates/hcw-window/src/governor.rs`，但 **`with_governor` 零生产调用**（`composition.rs:715` 明文"不接"） | W1 接线时一并评估：连 Governor 一起接，还是先只接装配内核 |
| **P2** OSA 来源维度 w4 | 装配/压缩面按来源加权 | 已落并有 A/B 机证（ADR-295 W4e：质量 on=10/off=0；工具 on=10/off=20） | **但** `with_source` 零生产调用（F11）⇒ w4 在当前生产路径上**不生效**。W1 是它生效的前提 |
| **P3** threads + 404 回放 | mca 传输级线程 | GATED（ADR-292/294），等 Anthropic 公测端点 | R12 不动 |

### 11.1 一个必须让决策者知道的事实

蓝图把"分层配额"作为核心机制，但仓内：

- `page_budget` 与 `tier_allocation` **零读取方**（全仓 grep 只命中定义、测试、事件构造，无任何决策分支消费；`window.rs:437-444` 只用 `resident_cap`）；
- `page_budget = 4_000` 硬编码两处（`governor.rs:138`、`:177`），只写进 `NexusEvent::WindowPlanApplied` 的 payload。

**含义**：蓝图 §5.1 的"R/S/E/M 四层按配额分配"目前是**设计契约**，不是运行行为。
R12 的 W1 若把装配内核接上，`tier_capacity` 才有第一个真实消费者——这是让蓝图 P1 从"类型落地"走向"行为落地"的最小一步。

### 12.1 角色与决策权

### 12.2 每波的收口门槛（三条，缺一不放行）

1. **L1 判据成立**，且附**一次真实的红**（植入坏例或翻转极性），红因与预期一致（不接受"rc≠0 即算红"）；
2. 行为变更带 **env 逃生** 且"关掉后逐字节等价旧路径"有测试；
3. 单 WP 单 commit，逐文件 `git add`，提交信息 HEREDOC。

### 12.3 影子期的安排（针对三个高风险翻默认）

| 项 | 影子期 | 判据 |
|---|---|---|
| W4 就绪派发翻默认 | ≥7 天双跑 | 同任务 `PlanSummary` 逐字段相等 + 无新增失败 |
| W5 `ConflictAware` 翻默认 | ≥7 天双跑 | 写集合不相交的判定被审计日志证实 + 无写序争议 |
| W3 cmt 生产者翻默认 | ≥1 轮观测 | 分层命中率与降级事件可解释 |

（影子期长度沿用 ADR-158 payload 级双跑先例；ADR-295 UD-4 的分级启用同款。）

### 12.4 不建议做的组织动作

- **不要**为 R12 单独开分支做全套改造：W1~W3 与调度线冲突面不同，混在一个分支会把"零冲突面"也拖进合并成本。
- **不要**先合流再重跑 R12 的全部度量：合流会改变基线，度量必须在最终基线上重采一次（W0 的基线报告要写明"基线提交"）。
