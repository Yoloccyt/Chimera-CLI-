## 1. 依赖类型学：把"能不能并行"拆成五种判据

工具调用之间不是"有边/无边"的二元关系。当前实现只识别其中两种，这是并行度受限的根源。

| # | 依赖类型 | 判据 | 现状是否识别 | 识别位置 |
|---|---|---|---|---|
| D-A | 数据依赖（显式边） | `PlanEdge.from → PlanEdge.to` | ✅ | `crates/nexus-contracts/src/spec/tool_plan.rs:88-93`；`toolplan_runner.rs:494-510` |
| D-B | 副作用依赖（二元） | `SideEffectDecl::{ReadOnly,Write}` + 未知按写 | ✅ | `tool_plan.rs:59-66`；`toolplan_runner.rs:537-568` |
| D-C | 资源冲突（读写集） | 两个写节点的写集相交、或写读相交 | ❌ | 无 |
| D-D | 时序依赖（审计序） | 写节点的**声明序**必须可复现 | ✅（以牺牲并行换取） | `toolplan_runner.rs:387-411` |
| D-E | 外部状态依赖（同一远端会话） | 同一 MCP server / 同一文件句柄 / 同一进程池 | ⚠️ 部分（per-provider 许可只在未合并分支存在） | 主线无；见 §6 |

**结论（事实）**：D-C 完全缺失 ⇒ 同层两个写不同资源的节点被迫整层串行（`toolplan_runner.rs:316-320`）；
D-E 在主线无任何约束 ⇒ 8 路并发可以同时打同一个 MCP server（`batch.rs:62-68` 只按"请求数"限流，
不按"目的地"限流），过订阅的代价落在 server 侧而非本进程。

## 2. 现状判定的三级优先级（必须原样保留）

`effective_side_effect` 的优先级是**安全契约**，任何 R12 改动不得调换（`toolplan_runner.rs:531-554`）：

1. 计划节点显式 `side_effect`（作者意图，实现方不得推翻）
2. `ToolExecutor::capability_of(tool)`（执行器自述单工具属性）
3. `ToolExecutor::declared_side_effects()` 批量表（配置驱动，如 MCP 只读清单）
4. 三者皆无 ⇒ `None` ⇒ 调用方 `node_is_read_safe` 保守判"可能写"（`toolplan_runner.rs:561-568`）

第 1 优先于第 2 的理由已写在源码里：否则接入方可把写操作自报为只读来换并发（`toolplan_runner.rs:533-536`）。
**R12 新增的 `AccessSet` 必须挂在这条链的同一位置（第 4 级之后、未知之前），不得抢占前三级。**

## 3. 目标：AccessSet（读写集）作为第 4 级判据

### 3.1 资源引用模型

```rust
// crates/nexus-contracts/src/spec/tool_plan.rs 追加（L0，纯类型，零依赖）
/// 资源引用 — 依赖冲突判定的最小单位
#[derive(Debug, Clone, PartialEq, Eq, Hash, Serialize, Deserialize)]
#[serde(rename_all = "snake_case", tag = "kind", content = "value")]
pub enum ResourceRef {
    /// 文件系统路径（规范化后的相对路径前缀；`**` 视作目录前缀）
    Path(String),
    /// 网络端点（`host:port` 或 provider id）
    Endpoint(String),
    /// 环境变量名
    Env(String),
    /// 进程/子进程组（如 `cargo` / `git`）
    Process(String),
    /// 宿主机全局互斥（终端、剪贴板、全局配置文件）
    Exclusive(String),
    /// 未知 — 与一切冲突（保守）
    Unknown,
}

/// 访问集 — 一次工具调用的读集与写集
#[derive(Debug, Clone, Default, PartialEq, Eq, Serialize, Deserialize)]
pub struct AccessSet {
    #[serde(default)] pub reads: Vec<ResourceRef>,
    #[serde(default)] pub writes: Vec<ResourceRef>,
}
```

### 3.2 冲突判定（纯函数，可 proptest）

```rust
/// 两个访问集是否冲突 — 冲突 ⇒ 不可并发（保守方向）
pub fn conflicts(a: &AccessSet, b: &AccessSet) -> bool {
    if a.reads.contains(&ResourceRef::Unknown) || a.writes.contains(&ResourceRef::Unknown)
        || b.reads.contains(&ResourceRef::Unknown) || b.writes.contains(&ResourceRef::Unknown)
    {
        return true; // 未知与一切冲突
    }
    // 写-写、写-读（双向）、读-写
    a.writes.iter().any(|w| b.writes.contains(w) || b.reads.contains(w))
        || b.writes.iter().any(|w| a.reads.contains(w))
}
```

**性质（需 proptest 锁定）**：
- 自反性：`conflicts(a, a)` 为真当且仅当 `a.writes` 非空
- 对称性：`conflicts(a,b) == conflicts(b,a)`
- 单调性：向任一集合**加入**元素不会使冲突由真变假（保守性不会因细化而丢失）
- 空集：`AccessSet::default()` 与任何非 Unknown 集合不冲突（纯只读、无外部副作用）

### 3.3 为什么不动 L0 的 `SideEffectDecl`

`SideEffectDecl` 只有两个变体且**没有 `#[non_exhaustive]`**（`tool_plan.rs:59-66`）。
给它加第三个变体会让所有下游 `match` 变成非穷尽 ⇒ 编译期破坏。因此：

- **不改** `SideEffectDecl`；
- **新增** `AccessSet` 为独立可选结构；
- 声明入口走 `ToolExecutor` 的**新增默认方法**（trait 加默认方法对既有实现零破坏）：

```rust
// gqep-executor/src/toolplan_runner.rs — ToolExecutor 追加（默认空 ⇒ 既有行为逐字不变）
fn declared_access(&self) -> Vec<(String, AccessSet)> { Vec::new() }
```

**装饰器穿透风险**：R11 的教训正是"新方法在装饰器链被丢弃导致并行封顶 = 0"（ADR-295 背景③，
`runtime.rs:295-309` 的 WHY 注释原文记录了这起事故）。因此 `declared_access` 与
`capability_of`/`declared_tools`/`declared_side_effects` 必须**同进同退**，并由静态门强制
（现有门 G-143 的判据是"四者同覆写"，R12 扩为"五者同覆写"，见 `07` 文 G-145）。

## 4. 执行面清单与并行现状

| # | 执行面 | 入口 | 并发上界（事实） | 屏障形态 | 依赖判据 |
|---|---|---|---|---|---|
| E1 | PlanRunner 层内 | `PlanRunner::run` | `DEFAULT_CONCURRENCY = 8`（`toolplan_runner.rs:181`），可 `with_concurrency` 覆写（`:196-203`） | 层间 barrier（`:247-264`）+ 写屏障分段（`:337-385`） | D-A + D-B |
| E2 | PlanRunner 混层 | `exec_layer_segmented` | 读段内 ≤8，写节点逐个 | 写节点整段串行（`:346-385`） | D-B + D-D |
| E3 | 批量派发 | `ToolRuntime::execute_batch` | `BatchLimits::default = 8 / 30s / 120s`（`batch.rs:57-69`） | 无屏障（无边），全局 deadline 绝对时刻（`batch.rs:194-200`） | 无（调用方假定无依赖） |
| E4 | Quest 波次 | `dispatch_in_waves` | 复用 E3 的 8（`commands/run.rs:239-259`） | **波间 await 串行**（`:232-233` 文档、`:215` 调用） | D-A（`topological_layers`） |
| E5 | Action 循环 | `run_action_loop` | `ACTION_CONCURRENCY_DEFAULT = 8`（`action_orchestrator.rs:351`），`CHIMERA_ACTION_CONCURRENCY` 可调（`:361-388`） | 许可耗尽时**在 recv 循环内同步跑**（`:431-437`） | 无（按事件独立） |
| E6 | 委派批次 | `chimera-mas/delegation.rs` | `DEFAULT_MAX_CONCURRENT_DELEGATION = 8`（R11 W5a 新增） | 无 | 无 |
| E7 | MCP 事务内扇出 | `mesh.execute_transaction` | 无显式上界，按 participant 数 `FuturesUnordered` | prepare/commit/rollback 三段各自扇出（`mesh.rs:354-430`、`:513-582`、`:674-690`） | 无 |
| E8 | 流式派发 | `StreamingDispatcher` | 无（**零生产消费者**） | 只读闭合即派发 / 写延后到轮末（`streaming_dispatch.rs:9-13`） | D-B |

### 4.1 已确认的五个结构性缺口

1. **E1/E4 的层（波）间 barrier 是纯等待**：宽 32 深 4 的只读 DAG 在 `c=8` 下有 4 次全层同步；
   若任一层存在长尾节点，后续层全部空转。【推断】在层宽不均时 makespan 损失可达单层最长节点时长 × 层数。
2. **E2 的写屏障粒度是"层"**：同层 1 个写节点会把该层切成"读段-写-读段"，而写节点之间即便写不同文件也逐个串行（`:346-378`）。
3. **E3/E4 无目的地感知**：8 个并发请求可能全部打到同一个 MCP server（`batch.rs` 无 provider 维度）。
   未合并分支 `feat/toolplane-execution` 已实现 per-provider 许可（见 §6），主线没有。
4. **E5 的背压降级是"在 recv 循环内同步执行"**（`action_orchestrator.rs:435`）——
   这不丢事件，但会把"其他动作"的接收也一起阻塞；在 `unlimited` 之外的任何有界取值下，长动作会拖住整个接收面。
5. **E8 整块能力未接线**：`StreamingDispatcher` 全仓仅被 `lib.rs:87` 声明与 `:102` 重导出，
   无任何生产构造点（grep `StreamingDispatcher::new` 仅命中自身测试）。

## 5. 可并行场景矩阵（六类执行面 × 判据 × 可提升空间）

| 场景 | 例子 | 当前行为 | 依赖类型 | 可并行? | 提升路径 | 风险 |
|---|---|---|---|---|---|---|
| S1 只读扇出（同层） | 并行读 8 个文件 | ✅ 已并行（≤8） | 无 | 是 | 上界自适应 | 磁盘争用 |
| S2 只读扇出（跨层） | L0 读完 → L1 再读 | ❌ 层 barrier | D-A 但只指向"自己的前驱" | 是（就绪即调度） | `LayerFree` 档 | 结果序不变，墙钟降 |
| S3 写不同资源（同层） | 写 a.rs + 写 b.rs | ❌ 整层串行 | 实为 D-C 无冲突 | 是（AccessSet 判定） | `ConflictAware` 档 | 审计序变化 ⇒ 默认关 |
| S4 写同资源（任意层） | 两次 edit 同一文件 | ✅ 声明序串行 | D-D 真依赖 | 否（必须串行） | 无 | 违反即不可复现 |
| S5 跨目的地扇出 | 8 个 MCP 调用打 3 个 server | ⚠️ 有 8 路上界但无 per-server 限 | D-E | 是（按 server 分桶） | ResourceGovernor | 单 server 被打爆 |
| S6 生成与执行重叠 | 模型流式产出 3 个只读调用 | ❌ 未接线 | 无 | 是 | 接线 `StreamingDispatcher` | 需真实流式面（见 §7） |
| S7 Quest 波次 | 4 波任务 | ❌ 波间串行 | D-A | 是（就绪即调度） | 与 S2 同构 | 同上 |
| S8 委派批次 | 16 个子代理任务 | ✅ ≤8 | 无 | 是 | 上界自适应 | 共享预算 |
| S9 动作循环 | TUI 连发 12 个动作 | ✅ ≤8，超出降级串行 | 无 | 部分 | 拆双车道（交互/后台） | 见 §6 per-provider 先例 |
| S10 子代理并行 | 一次派发 N 个子任务 | ⚠️ 受 `mas-sched` 租约 `max_concurrent=4` 与 `nexus-subagent` 的"禁嵌套 + Arena"约束 | 控制面 D-租约 / 数据面无 | 部分（控制面与数据面**不得强行贯通**，见 ADR-295 D8 的语义澄清） | 仅在数据面加界，不动租约配额 | 把控制面配额当数据面限流会误伤编排 |
| S11 后台常驻（ambient） | 看门狗 pause/resume 两循环、checkpoint 循环 | ✅ R11 W5c 已把两循环 `JoinSet` 批量化（输入受 `max_quests_per_batch=16` 界定） | 无（批内独立） | 是（已落） | 无需再改；checkpoint 循环**保持串行**（`checkpoint_async=true` 时 `save_checkpoint` 已是 fire-and-forget，批量化近零收益） | 再批量化属 churn |

**判定规则（给实施者的一句话）**：判定"可并行"只看 §3 的 `conflicts`；
判定"是否**允许**并行"再看 §7 的准入白名单。两者分离，避免把"技术上可并行"直接当成"默认并行"。

## 7. 不可并行（准入白名单）——以下情形一律串行

| 情形 | 理由 | 代码锚点 |
|---|---|---|
| 计划节点显式 `Write` 且与另一写节点冲突 | 写序必须等于声明序，否则审计链失序 | `toolplan_runner.rs:387-392` |
| 任一节点 `AccessSet` 含 `Unknown` | 未知即可能写，保守 | 本文 §3.2 |
| `PlanGuards::readonly_only == true` 时出现非只读节点 | 计划模式投影必须拒绝 | `toolplan_runner.rs:225-237` |
| 工具在 `declared_tools()` 中缺席 | 路由不可达，并发只会放大失败 | `toolplan_runner.rs:78-86` |
| MCP 事务的 prepare/commit 之间 | 2PC 两阶段语义 | `mesh.rs:235-330` |
| 模型流式产出尚未闭合的块 | 置信度门禁 <0.9 不派发 | `streaming_dispatch.rs:31-34`、`:252-261` |
| 预算已超限（`budget_bytes`） | 截断后继续执行会把"未执行"伪装成"执行过" | `toolplan_runner.rs:258-263` |

## 8. 并行度上界推导（不是拍 8，是从资源推）

设宿主逻辑核 `P`（`available_parallelism`，`main.rs:227-231` 已有旋钮但仅用于 worker 数），
工具类别权重 `w(class)`：

| 类别 | 判据 | 权重 | 语义 |
|---|---|---|---|
| `Io` | 文件/DB 读写 | 1/4 | 一个核可服务 4 个在飞 IO |
| `Net` | 远端调用 | 1/8 | 等待占比更高 |
| `Cpu` | 本地计算/解析 | 1 | 与核数 1:1 |
| `Exclusive` | 终端/全局锁 | ∞ | 恒串行 |

有效并发上界：

```text
effective_limit = clamp( floor(P / max_w(class_present)), 1, hard_cap )
其中 hard_cap 默认 8（与现状一致），可由 CHIMERA_TOOL_CONCURRENCY 覆写
```

**为什么默认仍是 8**：现状 6 处上界都是 8（§4 表），任何"默认改大"都会让 p99 变成不可归因的抖动；
R12 只做**按类加权**与**跨面共享预算**，默认值不变，变更走 `observe → apply` 两档（对齐 ADR-198 三态先例）。

## 9. 本章未验证项

1. 层 barrier 的真实损失比例 —— 需要 `plan_dag_layers` 基准（R12 W1 新建），当前无数据。
2. `dispatch_in_waves` 在生产中的实际层数分布 —— 依赖真实 Quest 语料，仓内无统计。
3. per-provider 许可对 MCP 场景的收益量级 —— 需 MCP 测试 server（未合并分支已有 `tests/mcp_stdio.rs` 可借用）。
4. E5 背压降级造成的接收面阻塞时长 —— 需 `action_orchestrator` 的 in-flight 观测，当前只有测试断言（`action_orchestrator.rs:1287-1288`）。
